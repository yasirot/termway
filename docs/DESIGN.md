## 1. 言語と依存: Rust

- wayland-client の pure Rust バックエンドを使うため、libwayland-dev も C コンパイラも要りません。コンテナで `cargo build` するだけで単一バイナリになります。
- 直接の依存は 9 個です: wayland-client / wayland-backend（`log` フィーチャのため）/ wayland-protocols-wlr / wayland-protocols-misc（仮想キーボード）/ flate2（バックエンドは zlib-rs）/ rustix / libc（`sigaction` と `prctl`）/ xxhash-rust / log。
- 自前で実装して依存を増やさなかったもの: base64、引数解析、ログ、PNG の書き出し（CRC-32 を含む）、端末モデル（テスト用）。

## 2. コンポジター: sway（cage は非推奨）

- **sway を採用。** 設定ファイルでボーダー・バー・Xwayland を無効化でき、カーソル非表示の設定もできます。
- **cage は、出力モードを変更すると `wlr_scene_output_layout_add_output: Assertion 'solo->scene_output != so' failed` で落ちます**（cage 0.1.5）。`--compositor cage --no-resize-output` なら動きますが、解像度は 1920×1080 固定です。
- **起動方法。** `$XDG_RUNTIME_DIR/termway-<pid>-<n>/` という専用の runtime dir を 0700 で作り、その中で起動します。ソケット名が確定するので、既存のセッションや他の残骸ソケットと衝突しません。調査時点で、`/run/user/1000` には lock ファイルのない `wayland-2`〜`22` が残っていました。D-Bus 用に `bus` へのシンボリックリンクを置きます。そのため、Firefox のように D-Bus で既存のインスタンスを探すアプリは、別の termway セッションのインスタンスも見つけて、そちらにウィンドウを開きます。
- **子プロセスの管理。** 専用のプロセスグループで起動し（端末からのシグナルを直接受けない）、`PR_SET_PDEATHSIG` を設定します（termway が SIGKILL されても終了する）。終了時はグループごと SIGTERM → 2 秒待って SIGKILL します。
- **sway でアプリが終わったら全体も終わる。** 起動スクリプトの最後で `swaymsg exit` を実行します。
- **利用者の sway の設定（`--sway-config`）。** バーやキー割り当て、隙間といった sway のデスクトップを、sway を入れ子にせずに使えるように、termway が生成する設定の最後で利用者の設定を `include` します。
  - 入れ子をやめた理由: 合成が 2 回になって CPU を余計に使ううえ、sway 1.11（wlroots 0.19）では内側の画面が 1 回おきに真っ黒になります（19 節）。1 つの sway に同じ設定を読ませると、真っ黒のフレームは出ませんでした。
  - 既定の設定（枠なし、ポインタを隠すなど）のあとに読み込むので、利用者の値が優先されます。出力のモードとスケールは、接続後に wlr-output-management で設定し直すので、termway の値（`--scale`）が残ります。
  - 設定ファイルは、runtime dir に置いたシンボリックリンク（`user.conf`）経由で読み込みます。sway は `include` のパスを wordexp で展開するので、パスに空白や引用符があると別のパスに分かれてしまいます。sway はリンクを実体のパスに解決するので、設定ファイルの中の相対パスの `include` は、その設定ファイルの場所から探されます。存在しない・通常のファイルでない場合は、コンポジターを起動する前にエラーにします。
  - コマンドを指定しなければ、起動スクリプトを作らず、アプリも起動しません（設定の `exec` に任せる）。セッションは sway の終了で終わり、ログには `sway exited (…)` と出ます。コマンドを指定した場合は、これまでどおりアプリの終了で終わります。
  - コマンドを指定せず、設定も何も起動しないと、画面は何の説明もなく真っ黒のままになります。見た目の設定（隙間と色）だけを書いた `~/.config/sway/config` を渡して、実際にそうなりました。sway は `-c` のファイルだけを読み、既定の設定と重ねないためです。そこで、5 秒たってもウィンドウが 1 つも開かなければ（`zwlr_foreign_toplevel_manager_v1` で数える）、`no window has opened` と警告します。
  - 設定の誤りは sway が黙って読み飛ばします（画面に赤いバーは出ます）。そこで、接続したあとにコンポジターのログから `Error on line …` の行を取り出し、警告として出します。sway は設定を読み終えてからクライアントに応答するので、接続が完了した時点で必ずログに出ています。行末のコメント（`output * bg … # …`）がエラーになるのに気づかず、壁紙もスケールも反映されていない、ということが実際にありました。
- **終わり方をログに出す。** sway は `exec` したコマンドの終了コードを報告しないので、起動スクリプトがアプリの終了コードを runtime dir の `app.status` に書きます（cage でも同じ）。コンポジターの終了後、この終了コードと、`zwlr_foreign_toplevel_manager_v1` で数えたウィンドウの数から終わり方を判断します。
  - 失敗（0 以外）: コンポジターのログの末尾を警告に含めます。アプリの stderr もこのログに入ります（既定では終了時に消えるため）
  - ウィンドウを 1 つも開かずに正常終了: 単一インスタンスのアプリ（Firefox など）が、既存のインスタンスに処理を渡して終わった可能性が高いので、その旨と対処を警告します。実際に、別の termway セッションの Firefox に空のウィンドウが増え続け、こちらは 4 秒で黙って終わる、という事例がありました
  - ウィンドウの数が分からない場合（cage）は、正常終了なら警告を出しません

### X11 のセッション（`--x11`、rootful の Xwayland）

i3 などの X11 のウィンドウマネージャーのために、termway の sway の中で Xwayland を rootful（X の画面全体を 1 つの Wayland のウィンドウにする）で起動し、その上でコマンドを動かします。キャプチャ・入力・リサイズは、今の Wayland の仕組みがそのまま使えます。Xvfb を使い、X11 用のキャプチャ（XDamage＋XShm）と入力（XTest）を新しく作る案は、`wl.rs` と同じ規模のものがもう 1 つ要るので採りませんでした。

起動スクリプトの流れ: Xwayland を `-displayfd` 付きで起動し、表示番号を FIFO で受け取ってから、コマンドを `DISPLAY` と `XAUTHORITY` 付きで実行します。コマンドが終わったら Xwayland を止め、sway を終了します。Xwayland が起動できなければ（表示番号が届かない）、コマンドは実行せず、終了コード 127 とログの末尾で報告します。PATH に Xwayland がなければ、コンポジターを起動する前にエラーにします。

2026-09-29 に Xwayland 24.1.10 と sway 1.11 で調べた結果です（i3 4.25.1、xterm）。

| 調べたこと | 結果 | 採用 |
|---|---|---|
| `-fullscreen` | X の画面は既定の 640×480（または `-geometry`）のままで、それを出力の大きさに引き伸ばして表示する。端末のリサイズにも追従しない | 使わない |
| 全画面にせず、sway にタイル配置させる（`default_border none` なので出力いっぱい） | X の画面がウィンドウの大きさになり、リサイズにも追従する（96×24 セル → 80×20 セルで 1920×1008 → 1600×840） | 採用 |
| `-hidpi` | X の画面が物理ピクセルになる（スケール 2 で 1920×1008、1.5 で 1694×992）。付けないと論理ピクセル（960×504）の画面を 2 倍に引き伸ばすので、ぼやける | 採用 |
| `-dpi 96×スケール` | Xft と pango で描く文字（i3 のタイトルとバー、`xterm -fa`）が、スケールに合った大きさになる。X のビットマップフォントは小さいまま | 採用 |
| `-shm` | sway は pixman で描くので、GPU のバッファ（glamor）は表示できない | 採用 |
| 真っ黒のフレーム | 出ない（100 フレーム中、起動直後の 2 フレームと終了時だけ）。入れ子の sway の不具合（19 節）とは違う | — |
| 認証 | `-auth` を付けないと、同じサーバーのほかのユーザーも接続できる。runtime dir に MIT-MAGIC-COOKIE-1 の cookie（FamilyWild、どの表示番号にも合う）を作り、Xwayland の `-auth` とクライアントの `XAUTHORITY` の両方に使う。cookie なしのクライアントは `Authorization required` で拒否された | 採用 |
| アプリの環境 | sway が設定した `I3SOCK` が残っていると、i3 は sway の IPC ソケットを自分のものとして作ろうとして起動できない。`WAYLAND_DISPLAY` が残っていると、foot などは X の画面ではなく外側の sway に開く。`WAYLAND_DISPLAY`・`SWAYSOCK`・`I3SOCK` を外し、`XDG_SESSION_TYPE=x11` にする | 採用 |
| termway の XKB キーマップ | LED（indicator）の定義がないと、i3 が起動時に送る `XkbGetIndicatorMap` の処理で Xwayland が segfault した。キーマップに Caps Lock・Num Lock・Scroll Lock の LED を足した（11 節） | 修正 |
| rootless の Xwayland（sway の `xwayland enable`） | distrobox（rootless の podman）の中では起動しない。コンテナの中から見るとホストの `/tmp/.X11-unix` の持ち主が `nobody` で、wlroots が `/tmp/.X11-unix not owned by root or us` で断る。rootful の Xwayland は警告（`Owner of /tmp/.X11-unix should be set to root`）を出すだけで動く | 既知の制約 |

- DPI は起動時のスケールから決めるので、途中でスケールが変わっても（別の DPI のモニターに移るなど）変わりません。X の画面の大きさは追従します。
- X の画面は 1 つの Wayland のウィンドウなので、sway が 1 回余計に合成します。

## 3. キャプチャ: wlr-screencopy の `copy_with_damage`

- Phase 2〜4 は `copy_with_damage` を使います。damage があるまで完了しないので、静止画面ではキャプチャ・エンコード・送信のすべてがゼロになります。初回と、リサイズ・失敗の後は `copy` を使い、全面を damage 扱いにします。
- Phase 1 は damage を使わず `copy` を固定 fps で繰り返します。Term.Everything と同じ「内容に関係なく毎フレーム全画面」の比較対象にするためです。
- wlroots 0.17.1 は damage の有無にかかわらず毎回全面を shm にコピーします。damage は変化した場所の情報としてだけ使います（`src/wl.rs`）。
- shm バッファは使い回し、サイズか形式が変わったときだけ作り直します。対応形式は XRGB/ARGB/XBGR/ABGR8888 です。`y_invert` フラグにも対応しています（その場合は damage 矩形の y 座標も反転する）。
- 捨てたもの: dmabuf（GPU がない前提）、`capture_output_region`（damage で十分）。

### 落とし穴: 約 1fps しか出なかった

`buffer_done` イベントを処理している中で `copy` リクエストを送ると、それは送信バッファに積まれるだけです。そのまま poll に入り、最大 1 秒（統計ティック）待ってから flush していました。sway 側のログでは copy から ready まで 11ms でした。**poll の直前に必ず flush する**よう修正しています（`app.rs` のイベントループ）。調査の途中で refresh=0 も疑いましたが、wlroots の headless バックエンドは 0 を 60Hz として扱うので無関係でした。念のため、リフレッシュは `max(60, --max-fps)` Hz を明示しています。

## 4. 出力解像度: wlr-output-management で設定

- 出力解像度は「セルサイズ × グリッド」にします（`--status-line` を付けたときは 1 行分減らす）。起動時とリサイズ時に `set_custom_mode` で設定します。sway の IPC ではなくプロトコルを使うので、コンポジターに依存しません。設定の完了を待つ処理には 5 秒のタイムアウトがあります（コンポジターが固まっても待ち続けない）。
- 変更できない場合（プロトコルがない、拒否された、`--no-resize-output`）は、フレームをグリッドに合わせて切り取るか、黒で埋めます。
- **出力スケール（`--scale`）**: 出力のモードは端末の物理ピクセルに合わせますが、アプリは論理ピクセルで文字の大きさを決めます。そのため Windows の 200% 表示の WezTerm（セルは 20×42px 前後）のような HiDPI の端末では、スケール 1 のままだと foot の文字が極端に小さくなります。既定の `auto` では「セルの高さ ÷ 21px」を 0.25 刻みに丸め、1〜4 に収めてスケールにします（9×21px の基準の端末では 1 なので、これまでと同じ）。Windows の表示倍率（125/150/175/200%）と同じ刻みです。
  - 起動時は sway の設定（`output * mode ... scale S`）で、リサイズ時は `set_custom_mode` と一緒に `set_scale` で設定します。別の DPI のモニターに移ってセルの大きさが変わっても追従します。
  - screencopy のバッファと damage は物理ピクセル（バッファ座標）なので、キャプチャ以降の処理は変わりません。仮想ポインタの `motion_absolute` は出力に対する比率なので、座標の変換も不要です。
  - 小数のスケールは、アプリが wp-fractional-scale に対応していれば、そのスケールで直接描かれます（foot 1.16 は対応）。対応していないアプリは整数スケールで描かれ、sway が縮小するため、少しぼやけ、CPU も使います。
  - モードを変える前に、待機中のキャプチャを取り消します。wlroots はモード変更をまたぐキャプチャを失敗させるため、取り消さないと、リサイズのたびに「screencopy failed」の警告が出ていました。取り消したキャプチャのイベントが遅れて届いても、今のキャプチャには反映しません（以前は今のキャプチャを失敗扱いにしていました）。出力設定の結果も、待っている設定のものだけを受け取ります。
  - キャプチャが失敗したら、50ms から 1.6 秒まで倍々に間隔を空けて取り直し、20 回続いたらエラー終了します（以前は 50ms 固定で、約 1 秒で終わっていました）。

## 5. 端末側の表示モデル（`src/render.rs`）

画面をタイル（既定は 1×1 セル）の「スロット」に分け、スロットごとに「いま何が見えているか」を管理します。

- **キャッシュタイル**: 内容ごとに 1 つの画像です。何か所にでも配置でき、LRU で管理します（Phase 3/4）。
- **一時画像**: Phase 1 のフレーム、Phase 2 の damage 矩形、Phase 4 の半解像度画像のような、タイル境界にそろった任意の矩形です。どのスロットにも見えなくなったら削除します。
- **単色タイル**: 画像ではなく、端末のセル背景として描きます（`SGR 48;2;r;g;b` と `ECH`）。端末画面は背景が多いので効果が大きく、ECH はカーソルを動かさないので、右下のセルでもスクロールが起きません。

### 重要: Kitty は同じ z の画像を「画像 ID 順」に重ねる

仕様には「同じ z-index で重なった場合、ID の小さい画像が下になる」と書かれています。配置した順ではありません。古い（ID の小さい）キャッシュタイルを新しい画像の上に置いても、下に隠れてしまいます。そこで次のルールにしています。

1. 配置は原則として重ねない。スロットの内容を変えるときは、先に古い配置を消す
2. 例外は「新しい一時画像を古い一時画像の上に置く」場合だけ（ID は単調に増えるので、正しく上になる）
3. Phase 4 では、タイルを `z=1`、一時画像を `z=0` にする。これで、半解像度画像の上に高画質化したタイルを重ねられる
4. 一時画像が物理的に覆っているスロットには、単色塗り（セル背景）を使わず単色タイル画像を置く。背景は画像より下に描かれるため

### 配置の削除方法

- **タイルと一時画像には配置 ID を使いません**（`p=` の 7 バイトを節約。スクロールの最適化のピースと WezTerm 互換モードは後述）。スロットの配置を消すときは、次のうち使える最短のものを選びます。
  - `d=c`（カーソル位置と交差する配置。一時画像が重なっていないスロットだけ）
  - `d=q`（セルと z を指定。Phase 4 で一時画像と重なっている場合）
  - `d=y`（行全体。後述）
  - `d=z,z=1`（Phase 4 で全面を半解像度にするとき、タイルを一括で削除）
- 一時画像は `d=I`（データも解放）、LRU から追い出したタイルも `d=I` で消します。
- 行一括削除: 1 行の中で入れ替わるタイルが多い場合は、`d=y`（約 22B）と「変化しないタイルの再配置」の合計を、「タイルごとの削除（約 19B）」と比べ、安い方を選びます。`ls -R` のスクロールでは変化しない行が多く、ほとんど選ばれませんでした。エディタのように全行が入れ替わる内容で有効です。
- 一時画像の面積が合計で 4 画面分を超えたら、全画面を 1 枚送り直して古いものをまとめて消します（ほぼ隠れた大きな画像が溜まり続けるのを防ぐ）。Phase 4 ではこの 1 枚を半解像度で送り、ふつうの高画質化で消えるようにしています。以前は等倍で送っていたため、動いている最中に全画面分の転送が発生していました。さらに、その画像は描き直されないスロット（静止したツールバーなど）の下に残り続けて、単色塗りと行一括削除が使えない状態が続いていました。

### WezTerm 互換モード（`--graphics-compat`）

WezTerm（20240203 と main のソースで確認）の Kitty graphics は、仕様と次の点で違います。そのため、上記の方式のままでは、マウスポインタの残像や文字の欠けが出ました。

- 画像をセルの属性として持つ。**削除は `d=a`/`d=A` と `d=i`/`d=I` しか実装されていない**（`d=c`/`d=q`/`d=y`/`d=z`/`d=r` は警告を出して無視される）
- **配置 ID なしで `a=p` を送ると、その画像の既存の配置を先に消す**。タイルキャッシュで同じ画像を別のスロットに置くと、前のスロットから消える
- 同じ z の画像は、セルの中で `binary_search` の位置に挿入される。そのため「新しい ID が上」にならない
- 画像はセルの大きさの断片に切られ、断片ごとにセルに付く。`X`/`Y` のずらしは断片の描画位置をずらすだけで、付くセルの数は画像の大きさで決まる（ずらした分は最後の断片が次のセルにはみ出して描かれる）
- ECH でセルを消去すると、配置 ID の**ない**画像の断片は消えるが、配置 ID のある画像の断片は消去後のセルに書き戻されて残る。EL/ED（`CSI K`/`CSI J`）はすべて消す
- **画像をセルに置くと、そのセルにすでにある配置 ID つきの断片が複製される。** `assign_image_to_cells` がセルを断片ごと複製してから新しい断片を足し、`Line::set_cell` が元のセルの配置 ID つきの断片をもう一度足すためです（WezTerm の #7953、修正案は #8035）。この不具合は 20240203 と 2026-09 時点の main の両方にあります。配置のたびに倍になるので、同じセルに置き続けると断片と描画する四角形（quad）の数が指数的に増え、WezTerm は応答しなくなり、メモリか頂点バッファの確保に失敗して落ちます

WezTerm モードでは、次のように出力します。

1. タイルの配置に、スロットごとに一意な配置 ID（スロット番号 + 1）を付ける。削除は `d=i,i=画像,p=配置` で行う
2. 行一括削除（`d=y`）は使わない。全画面を置き換えるときは、`d=z` の代わりに `d=a` で全配置を消す
3. 一時画像を、別の一時画像が覆っているセルの上に置くときは、先にそのセルを ECH で消去する。これで、同じ z の画像が 1 つのセルに重ならない（Phase 3 で、一時画像の上にタイルを置く場合も同じ）。一時画像には配置 ID を付けないので、ECH で消える
4. **配置 ID つきの画像（タイル）が残っているセルには、どの画像も置かない。** タイルを置き換えるときは先に消す。スクロールの最適化のピースには配置 ID を付けず、ピースを動かす前に範囲の上に重ねたタイルをいったん消す（後述）
5. 終了時の `d=R` は送らない（`d=A` が非表示の画像データも解放するため）

`auto`（既定）では、XTVERSION（`CSI > q`）の応答が `WezTerm` で始まるときに WezTerm モードにします。応答がない端末や、ほかの名前の端末は、これまでどおり仕様どおりのモードです。WezTerm の前に ConPTY などが入って応答が届かない場合は、`--graphics-compat wezterm` を指定します。

XTVERSION に応答がない端末では、スクロールの最適化を使いません（警告をログに出します）。kitty と Ghostty は応答するので、応答がないのは ssh.exe の後ろの WezTerm であることが多いためです。仕様どおりのモードのピース（`p=1` で置き直す）は、WezTerm では前述の複製を起こします。`--graphics-compat` を指定すれば使います。

`sim.rs` には WezTerm の挙動を再現するモード（`Flavor::WezTerm`）があります。断片の付き方、ECH と EL/ED の違いを再現し、未実装の削除、同じ z の断片の重なり、配置 ID つきの断片があるセルへの配置（上記の複製）をエラーとして検出します。仕様どおりのモードの出力を WezTerm のモデルに流すとエラーになることも、テストで確認しています。

以前のモデルは「ECH でセルの画像がすべて消える」「配置で断片は複製されない」と仮定していました。そのため、毎フレーム同じ配置 ID でピースを置き直し、ピースの境目の行や重ねたタイルのセルに置くスクロールの最適化の出力を、モデルが誤りとして検出できず、実機の WezTerm がスクロール中に応答しなくなって落ちる原因を見逃していました。

### 同一内容の判定

- タイル内容は xxh3-128（タイルの幅・高さを seed に入れる）で識別します。128 ビットにしたのは、長時間使っても衝突が事実上起きないようにするためです（衝突すると誤った表示が残る）。
- damage で変化したと通知されても内容が同じタイルは送りません（foot はカーソル行を再描画することが多い）。スロットごとに「表している内容」を保持し、比べています。

## 6. タイルキャッシュと LRU（`src/lru.rs`）

- 画面に出ているタイルはピン留めし、追い出しません。ピンが外れた時刻を最近使った時刻として扱います。
- 予算（`--cache-mb`、既定 128MiB）は、端末が画像を RGBA で持つと仮定して 4B/px で見積もります。kitty と Ghostty の既定の上限は 320MB なので、その半分以下にしました。1 画面分のタイルが入らない予算を指定した場合は、1 画面分まで引き上げてログに残します。
- リサイズ時はキャッシュを全部捨て、`d=A`（表示中を削除）と `d=R`（自分の ID 範囲を削除）を送ってから全画面を送り直します。

## 7. 圧縮: flate2 + zlib-rs、タイルはレベル 1

実フレームのタイル 491 個で測った結果です（`examples/zbench.rs`）。

| バックエンド / レベル | 1 タイル（9×21、567B）の時間 | 圧縮後の平均 | 全画面（2538×1260）の時間 | 全画面の圧縮後 |
|---|---:|---:|---:|---:|
| miniz_oxide L1 | 20.5 µs | 167 B | 9.0 ms | 105 KB |
| miniz_oxide L6 | 24.0 µs | 159 B | 27.0 ms | 64 KB |
| **zlib-rs L1** | **8.3 µs** | **141 B** | 15.9 ms | 149 KB |
| **zlib-rs L6** | 22.2 µs | 136 B | **15.0 ms** | **64 KB** |

小さなタイルは zlib-rs のレベル 1 が速くて小さく、大きな画像ではレベル 1 だと圧縮率が大きく落ちます。そのため `--tile-zlib-level`（既定 1）と `--zlib-level`（既定 6）の 2 系統にしました。圧縮後の方が大きくなる場合は無圧縮で送ります（`o=z` を付けない）。

### 並列化（`src/par.rs`、`src/zlib.rs`、`--threads`）

HiDPI の端末（200% 表示の WezTerm を最大化すると 3800×1890px、約 720 万画素）では、画面全体が動くと約 7fps しか出ませんでした。処理ごとの時間を測ると、次のとおりでした（1 フレームあたり）。

| 処理 | 初め | 対策後 |
|---|---:|---:|
| 半解像度への縮小 | 44ms | 6ms（1 画素ずつの境界判定と割り算をやめ、行から直接 2×2 平均を取る。結果はビット単位で同じ） |
| 大きな画像の zlib | 19ms | 分割して並列に圧縮 |
| shm → RGB の変換 | 14.5ms | 行で分けて並列 |
| タイルのハッシュ | 12ms | タイルを分けて並列 |

最初は圧縮が原因だと考えましたが、圧縮レベルを 6 から 1 に下げても 7.9fps が 8.2fps になっただけでした。測ってから直す順番を決めています。

- スレッドは `std::thread::scope` で毎回起動します（プールや rayon は使いません）。1 フレームは数十 ms で、スレッドの起動は数十 µs です。既定のスレッド数は CPU 数で、コンポジターとアプリの分を残すため最大 8 にしています。
- zlib の並列化は pigz と同じ方式です。入力を 256KiB 以上の塊に分け、塊ごとに独立した raw deflate で圧縮し、sync flush でバイト境界にそろえてつなげます。先頭に zlib ヘッダー、最後に全体の Adler-32（塊ごとの値を `adler32_combine` で合成）を付けるので、普通の zlib デコーダーで読めます。圧縮率の低下は、テストのデータで 10% 未満です。
- 並列にしても結果は変わりません（変換とハッシュは同じ値、zlib は展開すると同じデータ）。テストで確認しています。
- 結果: 3800×1890px で画面全体が動き続ける場合、`--threads 1` の 9.8fps が 8 スレッドで 16.2fps になりました。残りは sway の pixman 描画と screencopy のコピー（1 フレーム 40ms 前後）です。

## 8. Kitty への出力

- 画像は `f=24`（RGB）で送ります。Ghostty には、32 KiB を超える画像を PNG（`f=100`）で送ることがあります（後述）。どの命令にも `q=2` を、配置には `C=1` を付けます。ただし起動時の対応確認 `a=q` だけは応答が必要なので `q` を付けません。
- チャンクは base64 で 4096B ごとに分けます（4 の倍数）。2 つ目以降のチャンクは、仕様どおり `m` と `q` だけにします。`q=2` をすべてのチャンクに付けるのは、応答を確実に抑止するためです。
- 1 フレーム分の出力を DEC 2026（synchronized output）で囲みます（`--no-sync` で無効化）。対応していない端末では無視されるだけです。途中の状態が描かれないので、削除してから配置する順序でもちらつきません。
- カーソル移動は現在位置を追跡して、`CUP` と `CUF`/`CUB` の短い方を使います。
- 画面を汚さないため、代替画面（`?1049h`）・カーソル非表示・自動折り返し無効（`?7l`）で描画します。

### Ghostty 1.3: 大きな画像は PNG で送る（`--large-images`）

macOS の Ghostty から「画像がところどころ欠け、そのうち落ちる」という報告がありました。Ghostty 1.3.1 の端末部分（VT の解析と Kitty graphics の処理）をライブラリとしてビルドし、termway の出力を流して調べました。

- **原因**: Ghostty 1.3 は `o=z` の画像を Zig 0.15.2 の `std.compress.flate` で展開します。その固定ハフマンブロックの処理は、一致（長さと距離）を書く前に出力先の空きを確かめません（動的ハフマンブロックでは確かめる）。展開は 64 KiB の窓を使い回すので、固定ハフマンブロックの一致が窓の境目をまたぐと `unreachable` に達します。リリースビルドでは未定義動作になり、手元の x86_64 ではセグメンテーション違反でした。
- **頻度**: `ls -R` を流し続けたときの出力で、1×1 タイルでは大きな画像 598 枚のうち 1 枚、`--tile 4x2` では 10 秒間に 7 枚が当たりました。Python の zlib ではどれも正しく展開できるので、termway の出力は正しい zlib です。
- **Ghostty 側**: main では 2026-09-28 に、高速化を目的として展開を wuffs に置き換えました（PR #14422）。PR ではこの不具合に触れていません。1.3.1 までのリリースには残っています。
- **対策**: XTVERSION の応答が `ghostty` で始まる端末には、32 KiB を超える画像を PNG（`f=100`）で送ります。Ghostty は PNG も wuffs で展開するので、この不具合に当たりません。中身は今と同じ zlib（並列圧縮も同じ）で、各行の先頭にフィルタ種別 0 の 1 バイトを付けるだけです。増えるのは 1 行あたり 1 バイトと、チャンクの約 60 バイトです。
  - 32 KiB にしたのは、この不具合が窓（64 KiB）を使い切ってから起きるためで、半分にして余裕を取りました。タイルはこれより小さいので、今までどおり zlib です。
  - Ghostty のどの版にも PNG を使います。版で分けるほどの差がないためです。`--large-images zlib|png` で上書きできます。
- **回帰テスト**: `sim.rs` に、zlib で展開した画像が 32 KiB を超えたらエラーにする制限（`zlib_limit`、Ghostty 1.3 のモデル）を足しました。fake-term は既定で Ghostty 1.3.1 として応答するので、この制限も有効にします。e2e はすべてこの条件で通ります。`--large-images zlib` の出力が拒否されることも確かめています（`ghostty_zlib`）。

### Phase 1 の 2 枚交互

同じ ID で再送すると、既存の配置が消えてから新しい画像になります（仕様）。Phase 1 は毎フレーム新しい ID で送って配置し、そのあとで前の画像を削除します。一時画像を回収する一般的な仕組みで、自然にこの順序になります。

## 9. Phase 4（段階的高画質化）

- 1 フレームで実際に変化したタイルが全体の `--lowres-threshold`（既定 5%）以上なら「動いている」とみなし、変化したタイルを矩形にまとめ（余白 30% まで許容）、2×2 平均の半解像度画像を `c=`/`r=` で拡大表示させます。それ未満（タイピングなど）は通常のタイル処理です。
- 高画質化の条件: 半解像度のタイルが `--refine-delay-ms`（既定 200ms）以上経ち、かつ次のどちらかを満たすこと。
  - そのタイルが **2 回のキャプチャで変化しなかった**
  - コンポジターから **damage が 200ms 来ない**（キャプチャのリクエストが待たされたまま = 画面全体が静止）
- **時間だけで判定しない理由。** 最初は時間だけで判定していました。回線が細いとフレーム間隔が 200ms を超えるため、動いている最中でも毎回全面を高画質で送り直し、Phase 3 より悪い 0.3fps になりました。現在の条件にしてから 11.6fps です（2.5MiB/s 制限下）。
- 1 枚の半解像度画像が覆うスロットがすべて高画質化できるときは、先にその画像を消します。そうすると、単色タイルを「セル背景」で描けます（背景色が前と同じなら 0 バイト）。
- 余白の許容率は 0 / 0.1 / 0.3 / 0.6 を実測し、0.3〜0.6 が最良でした。0 にすると矩形が細切れになり、画像数と高画質化がかえって増えます。

### スクロールの最適化（`src/render/region.rs`、`src/scroll.rs`）

半解像度で送る方式では、スクロールのたびに範囲全体を送り直します（画素数は 1/4 ですが、範囲の面積に比例します）。ブラウザのスクロールは「前のフレームが上下にずれただけ」なので、送信済みの画像をずらして表示し、**新しく見えた帯だけ** を等倍で送ります。

- **検出**: 画素の行ごとに、横 8 本の帯に分けて xxh3-128 のハッシュを取ります。前のフレームで 1 回しか出てこない帯のハッシュだけを使って、ずれ量 `dy` を多数決で決めます（空行のように何度も出てくる行は、どこへずれたか区別できないため）。帯に分けたのは、スクロールバーやサイドバーやポインタで 1 つの帯が崩れても、ほかの帯で判定できるようにするためです。
- **一致の判定**: 各行について、情報を持つ（一度しか出てこない）帯だけを見て、その過半数が一致すれば「一致」とします。最初は空白の帯も数えていたので、less の新しい行が下のプロンプト行と「一致」してしまい、動いている帯を最下行まで広げていました。
- **範囲**: 画面の全幅のタイル行です。一致した行から「実際に動いている帯」を求め、そこに丸ごと収まるタイル行だけを範囲にします。動かない行（less のプロンプト、ページ内の固定ヘッダー）を範囲に入れると、新しく見えた帯としてその行を取り込み、古い写しがずれながら 1 フレームに 1 本ずつたまっていきます（実測で差分タイルが 180 → 910 枚に増えました）。
- **ピース**: 範囲を隙間なく覆う横長の画像の並びです。ずらすときは、全ピースを切り出し位置（`x,y,w,h`）とセル内のずらし量（`Y`）を変えて置き直し（`a=p` を同じ `p=1` で）、新しく見えた帯を 1 枚のピースとして送ります。範囲から出たピースは `d=I` で消します。ピースが 32 枚を超えたら、隣り合うピースのうち合計の高さが最小の組を 1 枚にまとめて送り直します（1 回ごとの置き直しの命令を抑えるため）。
- **ベース**: ピースが表示している画素と、その行ハッシュを、行のリングバッファで持ちます（ずらすときにコピーしない）。新しいフレームとベースが違うタイルだけ、ふつうのタイル（`z=1`、タイルキャッシュを使う）を上に重ねます。スクロールバー、固定表示の要素、ポインタがこれに当たります。行と帯のハッシュが一致するタイルは、画素を比べずに「同じ」とみなします（128 ビットなので、タイルキャッシュの鍵と同じく衝突は考えません）。
- **始める条件**: 2 フレーム続けてずれを検出し、動いている帯が 4 タイル行以上あること。一度きりの小さなスクロールで、範囲全体を等倍で送らないためです。
- **やめる条件**: 1 フレームで変わったタイルが範囲の半分を超えたとき（ページ遷移など）、ずらしたあとも差分が範囲の 1/4 を超えるとき、ずれが範囲の高さの 1/4 を超えるときです。最後の条件は、新しく見えた帯を等倍で送るより、範囲全体を半解像度で送る方が安くなる境目です（`ls -R` を流し続ける場合がこれに当たります）。やめると、範囲のタイルはふつうの処理で描き直します。
- **重ね順**: ピースは一時画像と同じ `z=0`、上に重ねるタイルは `z=1` です。隣り合うピースは 1 つのセルを上下で分け合いますが、画素は重なりません。WezTerm では、置き直す途中で動かしたピースがまだ動かしていないピースに重ならないよう、下へのスクロールでは下のピースから順に置き直します（`sim.rs` の WezTerm モデルは、同じ z の画像の重なりを画素単位で検出します）。
- **Kitty の削除**: 範囲のスロットは「覆われている」扱い（`cover` に 1 を足す）にしてあります。そのため、上に重ねたタイルの削除は `d=c` ではなく `d=q,z=1` になり、ピースを巻き込みません。
- **WezTerm**: 配置 ID つきの断片があるセルに画像を置くと、その断片が複製されます（前述）。ピースに配置 ID を付けると、境目の行を共有するピースどうしで、上に重ねたタイルがあればそのタイルも、置き直すたびに倍になります。静止したまま重なり続けるタイル（余白の上のポインタ、スクロールバー、固定表示のボタン）は毎フレーム倍になり、1 秒ほどで数千万個になって WezTerm が固まっていました。そこで WezTerm では、ピースに配置 ID を付けず、ピースを動かす前に範囲の上のタイルを消し、動かしたあとで必要なものを置き直します（キャッシュに残っているので配置命令だけ）。WezTerm は配置 ID のない `a=p` でその画像の既存の配置を置き換えるので、これが置き直しとして働きます。
- ピースの置き直しは、差分の判定で範囲をやめないと決まってから行います（やめる場合は置き直さずに消す）。
- 結果（less で毎秒 30 行、3800×1890px）: 1.73 MiB/s・15fps・半解像度が、768 KiB/s・25.6fps・等倍になりました。1 フレームの処理は約 10ms でした（行ハッシュ 1.7ms、ずらしと帯の送信 1.9ms、差分の判定 1.0ms。ピースのまとめ方とずれの上限を決める前の計測）。

## 10. 端末との初期ハンドシェイク（`src/term.rs`）

- 送る問い合わせ: Kitty graphics の `a=q`、`CSI 16 t`、`CSI 14 t`、`CSI ? 1016 $ p`（SGR-Pixels 対応の確認）、XTVERSION（`CSI > 0 q`、端末名。WezTerm 互換モードの判定に使う）、最後に DA1（`CSI c`）。
- どの端末も DA1 には順序どおりに答えます。そのため **DA1 の応答が届いた時点で問い合わせは全部終わった**と判断でき、未対応の問い合わせのために 1 秒待たずに済みます。DA1 も来なければ 1 秒でタイムアウトし、エラー終了します。
- セルサイズの決め方（この優先順）:
  1. `--cell-size`
  2. `CSI 16 t` の応答（0 や不正な形式ならエラー）
  3. TIOCGWINSZ のピクセル値（distrobox 経由では 0）
  4. `CSI 14 t` ÷ グリッド
  5. どれも得られなければ「CSI 16 t に応答がない」エラー
- ハンドシェイク中に打たれたキーは捨てます。
- リサイズのとき TIOCGWINSZ にピクセル値がなければ `CSI 16 t` を送り直し、1 秒待ちます（来なければ前のセルサイズのまま）。問い合わせは送信中のフレームの後ろに並ぶので、遅い回線では応答が 1 秒より遅れることがあります。遅れて届いた応答も、セルサイズが違えば反映します。
- DECRPM で 1016 の状態が 4（恒久的に無効）なら、SGR-Pixels は使いません。

## 11. 入力（`src/input.rs`、`src/keymap.rs`）

- stdin を raw モードにして、従来型のキー表現（C0 制御文字、`CSI`/`SS3` のカーソル・ファンクションキーと xterm 形式の修飾子、ESC 前置の Alt）、SGR マウス（1000/1002/1003/1006）、端末の応答（`CSI … t`、DA1、DECRPM、APC G）を解析します。途中で切れたシーケンスは次の read まで保持します。単独の ESC は 25ms（終了キーが ESC のときは 150ms）待ってから Escape キーに、ESC と `[` `O` `]` などシーケンスを始める 1 文字だけなら Alt+文字に確定します。それより長い途中のシーケンス（回線の途中で分かれたマウス報告や応答）は 500ms 待ち、残りが来なければ捨てます。以前は途中のシーケンスをすべて「Escape キー＋残りの文字」にしていたため、Alt+] や、遅れて届いたマウス報告で、既定の終了キー ESC が働いてセッションが終わることがありました。rxvt 式の「ESC＋カーソルキー」は Alt+カーソルキーとして扱います。SGR マウスの座標が負（ウィンドウの外へのドラッグ）でも、0 に丸めて扱います（ボタンを離した報告を捨てると、押されたままになる）。
- キーマップには、使わない LED（Caps Lock・Num Lock・Scroll Lock）も定義しています。定義がないと、`XkbGetIndicatorMap` を送る X のクライアント（i3 など）が接続したときに、Xwayland（24.1）が segfault しました（2 節の X11 のセッション）。
- 仮想キーボードには自前の XKB キーマップを送ります。ASCII の文字は US 配列での本来の evdev コードに割り当てるので、ショートカットが普通に動きます。それ以外の文字（IME の確定文字列や貼り付け）は、`0x300` 以降のコードに動的に割り当てて（最大 64、LRU で再利用）キーマップを送り直します。1 回の読み込みに 64 種類を超える文字がある場合（日本語の長い貼り付け）は、64 種類ずつに分けて、キーマップを切り替えながら送ります（以前は前半の文字が同じ読み込みの後半に追い出され、黙って失われていました）。修飾キーは `modifiers` リクエストで直接設定します。
- マウスは `create_virtual_pointer_with_output` で出力に紐付け、絶対座標で送ります。端末が SGR-Pixels（1016）に対応していればピクセル座標を、そうでなければセルの中心を使います。foot のセルを 9×21 に揃えた状態で、ピクセル (86,95) のクリックが foot にセル (10,5) として届くことを確認しました。
- 終了キーは要件どおり既定で ESC です。ただしそうすると ESC をアプリに送れないため、`--quit-key ctrl-]` と `none` を用意しました。

- キーをコードポイントで表す形式も読みます。xterm の modifyOtherKeys（`CSI 27 ; 修飾 ; コード ~`）と fixterms（`CSI コード ; 修飾 u`）です。Ghostty は、アプリが何も要求していなくても、Shift+Enter・Ctrl+Enter・Alt+Shift+Enter をこの形（例: `CSI 27;4;13~`）で送ります。以前は読まずに捨てていたので、Ghostty では i3 の `$mod+Shift+Return` が効かず、foot でも Shift+Enter が何もしませんでした（2026-09-29）。WezTerm は、アプリが CSI u や modifyOtherKeys を有効にしない限り、Alt+Shift+Enter を Alt+Enter と同じ `ESC CR` で送ります。また、WezTerm は既定で Alt+Enter を全画面の切り替えに使うので、Alt+Enter はアプリに届きません。

### 捨てたもの

- **Kitty keyboard protocol**: キーの押下/解放や曖昧さのない修飾子を得られますが、Ghostty での挙動が未確認なので見送りました。今は押下と解放を同時に送るため、キーリピートやキーを押し続ける操作は再現できません。
- **ブラケットペースト**: 有効にしていません。貼り付けは文字の連続として入力されます。

## 12. 出力スレッドと流量制御（`src/writer.rs`）

- 端末への書き込みは専用スレッドで行います。回線が遅くても、入力処理とシグナル処理が止まりません。
- 終了時は、書き込み中のフレームを書き終えるまで待ち、まだ書き始めていないものは捨てます。待つのは端末が読み続けている間（書き込みが 3 秒止まったら諦める。上限 60 秒）です。以前は一律 3 秒で諦めていたため、遅い回線で大きなフレームを送っている最中に終了すると、画面を戻せず、マウス報告が有効なままの端末が残りました。
- **同時に送る途中のフレームは 1 つまで。** 書き込みが終わってから次のキャプチャを要求します。damage はコンポジター側で合算されるので、遅い回線では自然に fps が下がり、キューが溜まって遅延が伸びることはありません。
- 各フレームはまるごと書き終えてから次に進むので、終了処理のエスケープシーケンスが画像転送の途中に割り込むことはありません。

## 13. 後始末（あらゆる終了経路）

- `Terminal` 構造体の Drop で、書き込みスレッドの完了を待ち（最大 3 秒）、後始末のシーケンスを送り、termios を戻します。
  - 後始末のシーケンス: `d=A` と `d=R`（1〜2³²−1。WezTerm モードでは `d=A` だけ）、SGR リセット、画面消去、マウス報告の無効化、`?7h`、`?25h`、`?1049l`、最後に DA1（`CSI c`）
  - DA1 の応答が来るまで（最大 300ms）入力を読み捨て、残りも捨ててから termios を戻します。マウス報告の無効化が端末に届く前に送られた報告が、終了後のシェルに文字として出るのを防ぐためです
- コンポジターは、プロセスグループごと SIGTERM で止めます（2 秒待っても終わらなければ SIGKILL）。ただし sway の `exec` はアプリごとに `setsid` するので、アプリは sway のグループに入りません。foot は Wayland の接続が切れると自分から終わりますが、入れ子の sway やデーモンは残ることがあります。そこで、セッション内のプロセスがすべて引き継ぐ専用の `XDG_RUNTIME_DIR` を目印にして、`/proc/*/environ` から探して止めます（SIGTERM、1 秒後に SIGKILL）。ディレクトリ名に termway の PID が入っているので、ほかのセッションのプロセスとは混ざりません。
- `WLR_BACKENDS=headless` などのコンポジター用の環境変数は、起動スクリプトの中で termway 起動時の値に戻してからアプリを起動します。戻さないと、入れ子の sway がヘッドレスで起動して、何も表示されずに残ります。
- この後始末が行われる経路:
  - ESC / Ctrl-]
  - SIGINT / SIGTERM / SIGHUP / SIGQUIT（self-pipe で受ける）
  - アプリの終了（Wayland 接続が切れたらコンポジターの終了を確認）
  - パニック（`panic=unwind` と `catch_unwind` で巻き戻す）
- 端末が読まなくなって書き込みスレッドが終わらない場合は、画面の復元は諦めて termios だけ戻します（エラーとして報告）。
- **SIGKILL では何もできません**（コンポジターは PDEATHSIG で終了します）。
- 検証内容:
  - fake-term が、終了後に「画像が残っていない」「代替画面から戻っている」「pty の ICANON と ECHO が戻っている」ことを確認する（`scripts/e2e.sh`）
  - 入れ子の sway を起動し、終了後にそのプロセスが残っていないことを確認する（`scripts/e2e.sh` の `nested_sway`）。fake-term は pty を CLOEXEC で開きます。以前は pty の fd が termway から sway とアプリへ漏れ、残ったプロセスが pty を開いたままにしていたため、fake-term が終われませんでした
  - アプリの終わり方のログ: foot の正常終了では警告を出さないこと、ウィンドウを開かずに終わるアプリ（`sh -c 'sleep 1'`）と失敗するアプリ（終了コード 3、stderr に出力）では、それぞれの警告と出力が出ること（`scripts/e2e.sh` の `app_exit`・`no_window`・`app_failed`）
  - `--sway-config`: 設定の背景色が隙間に映ること、アプリを起動しないこと、`swaymsg exit` でセッションが終わって `sway exited` と出ること、行末のコメントのエラーが `sway config: Error on line` として出ること、アプリを起動しない設定では `no window has opened` と出ること（`scripts/e2e.sh` の `sway_config`・`sway_config_exit`・`sway_config_empty`）
  - `--x11`: HiDPI の端末で X の画面が物理ピクセル（1920×1008）になり、リサイズに追従すること（i3 の `get_outputs` で確かめる）、cookie のないクライアントが拒否されること、i3 の終了でセッションが終わって Xwayland が残らないこと（`scripts/e2e.sh` の `x11_i3`・`x11_exit`）。起動スクリプトは、Xwayland を代わりのスクリプトに置き換えたユニットテストで、表示番号の受け取り・環境の入れ替え・Xwayland の停止・起動失敗の報告を確かめる
  - パニックの経路はユニットテストで確認（`app::tests::panic_restores_terminal`）

## 14. ログと出力の分離

- stdout には描画しか書きません。セッション中は stderr も同じ端末なので、ログは `--log` のファイルに書くか、メモリに溜めて終了後（端末を戻した後）に表示します。
- wayland-backend は `log` フィーチャが無効だと、接続断などで **stderr に直接 `eprintln!` します**。`log` フィーチャを有効にし、そのメッセージを自前のロガーに転送しています。
- wayland-backend は、呼び出し元に返すエラーをすべて ERROR でもログに出します。アプリの終了で sway が接続を切ったときの `Broken pipe` もその 1 つで、正常終了なのに原因のように見えていました。termway は返ってきたエラーを自分で報告するので、このメッセージは DEBUG に下げています（`-v` で見える）。
- パニックのメッセージも同様に、端末を戻してから表示します。
- stderr への書き込みの失敗は無視します（`eprintln!` は失敗すると panic する）。SSH が切れると、端末への書き込みは EIO になります。以前は終了時のログ表示で panic し、panic フックが保持中のロガーのロックを取りにいって、プロセスが固まったまま残っていました。ロガーは同じスレッドからの再入を検出して何もしません。
- `--stats` のファイルに書けなくなっても（ディスクが一杯など）、警告を出して統計の書き込みをやめるだけで、セッションは続けます。

  - fake-term は、出力が 800ms 止まった時点で画面のスナップショットを取ります。Phase 1 は固定 fps で送り続けるので止まりません。そのため、終了予定時刻から 2 秒たったら、同期出力（DEC 2026）のフレームの切れ目で取ります。以前はスナップショットが作られず、e2e が前回の古いファイルと比べていました。いまは各ケースの前に古い成果物を消し、スナップショットがなければ失敗にします
- **実機の Ghostty と WezTerm での確認は、利用者からの報告だけです**（下記の未確認事項を参照）。WezTerm のモデルは、ソース（20240203-110809-5046fc22）を読んで作りました。

## 16. 未確認事項（前提にしていないこと、または実機で確認が必要なこと）

## 17. 捨てた案

| 案 | 捨てた理由 |
|---|---|
| Unicode プレースホルダー（U+10EEEE）で配置する | 1 タイルが数バイトの文字で済み、削除も不要になる。ただし Ghostty での対応が未確認なので見送った。最も有望な次の一手 |
| タイルをまとめたアトラス画像と `x,y,w,h` による切り出し | 圧縮効率は上がるが、配置コマンドが長くなる。定常状態では配置が大半を占めるので不利 |
| 行単位のタイル（1 行 = 1 画像） | スクロールで行が移動すると再配置 1 回で済む。一方、新しい行は 1 行まるごと送る必要がある。セルを揃えた 1×1 タイルの方が小さかった |
| 配置 ID によるスロット単位の置き換え | 同じ画像 ID のときしか置き換わらない仕様なので、キャッシュの共有と両立しない |
| `C=0` でカーソルを進めて移動コマンドを省く | 要件の `C=1` に反する。さらに最下行でスクロールする危険がある |
| 全画面を送る Phase 1 を damage 駆動にする | 比較のための基準にならないため、固定 fps のままにした |

## 18. Phase 5 のメモ（範囲外）

サーバー側とクライアント側のヘルパーに分ける構成です。

- サーバー側: 今と同じ damage とタイルの処理を行い、独自形式（タイル ID、配置、削除、半解像度の矩形）を zstd の辞書付きストリームで送る。グリフのタイルは似ているので、辞書が効くはず
- 手元のヘルパー: ストリームを展開し、Ghostty に `t=s`（POSIX 共有メモリ）で RGBA を渡す。base64 の 4/3 倍と、エスケープシーケンスの解析コストがなくなる
- 期待できる効果: 回線上のバイトがさらに減る（base64 分と、配置コマンドのバイナリ化）。端末側では共有メモリを使うので、1 画面分の大きな画像でも転送が軽くなる
- 検討すべき点: ヘルパーの配布（手元に常駐させる必要がある）、SSH 上の多重化（`ssh -L` やサブシステム）、Ghostty が `t=s` に対応しているかの確認

## 19. 技術的負債・今後

- 画面全体が大きく変わり続ける場合は、sway の pixman 描画と screencopy のコピー（1 フレーム 40ms 前後）が上限になります。GPU があるなら、sway を GLES2 で動かす選択肢を足す余地があります。
- スクロールの最適化は縦方向だけで、範囲は全幅のタイル行です。部分的にしか動かない端のタイル行（foot の行とセルの高さが揃わない場合など）は、ふつうのタイル処理で毎フレーム描き直しています。
- 計測結果（[BENCHMARK.md](BENCHMARK.md)）の表は初版の環境のものです。並列化とスクロールの最適化のあとの再計測は、まだ暫定値だけです。
- **Ghostty の描画は、画像の配置の数に比例して重くなります。** Ghostty（1.3.1、2026-09 時点の main も同じ）は、フレームを描くたびに、配置ごとに GPU のバッファを作って描画命令を出し、テクスチャも画像ごとに別です（`src/renderer/image.zig`）。WezTerm は画像をグリフと同じアトラスに入れて、まとめて描きます。
  - termway は文字のあるセルごとにタイルを置くので、less で文章を表示した 190×50 セル（16×34px）の画面では、配置が約 1,600 になりました。`--tile 4x2` では約 250、`--phase 2` なら 4 以下です。
  - 端末部分の処理は問題ありません。10 秒分のページスクロールの出力を 0.64 秒で処理しました。ただし `d=c`/`d=q`/`d=y` はすべての配置を調べるので、配置が多いと 1 回 30µs ほどかかります（`d=i,p=` は 0.1µs）。
  - macOS の Ghostty で遅いという報告の原因と考えていますが、実機での切り分けはまだです。対策の候補: 広い範囲の高画質化を 1 枚の画像で送る、画面が落ち着いたら配置をまとめる。
- **sway 1.11（wlroots 0.19）で sway を入れ子にすると、内側の画面が 1 回おきに真っ黒になります。** 原因は特定できていません。2026-09-29 に分かったことは次のとおりです（外側・内側とも sway 1.11、pixman）。
  - termway が取得したフレームそのものが、内側の sway が描き直すたびに「全部映る」と「完全に真っ黒（時計の部分も映らない）」を交互に繰り返す。バーの時計があれば 1 秒おき
  - damage を使わない `--phase 1` でも同じ。端末の大きさや互換モード、内側の設定（`exec foot` とバーだけでも起きる）にもよらない
  - 内側・外側・両方に `WLR_SCENE_DEBUG_DAMAGE=rerender`（毎フレーム全体を描き直す）を付けても変わらない。damage の追跡の問題ではない
  - IPC で見ると、外側では内側のウィンドウが表示されたまま、内側の出力も有効なまま。どちらのデバッグログにもエラーはない
  - foot を直接動かした場合と、1 つの sway に同じ設定を読ませた場合（`--sway-config` と同じ構成）は、真っ黒のフレームが 0
  - そのため、内側の sway の wayland バックエンドが外側にバッファを渡すところ（wlroots 0.19）に原因があると見ています
  - e2e の `nested_sway` は、この状態でも通っていました。最後のフレームを比べるだけなので、映っている方のフレームで一致したためです。途中の真っ黒なフレームを検出するには、`fake-term --dump-output` の出力を同期出力の区切りごとに `sim.rs` で再生し、各フレームを調べる必要があります
- XKB キーマップは自前で書いています。キーボード配列を指定する機能はありません（US 配列固定）。
- `--attach` で接続した既存のコンポジターでは、アプリを起動しません。出力モードは変更します。
- クリップボード（`wl_data_device`）とカーソル形状の連携はありません。

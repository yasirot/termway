### 計測方法

実機の Ghostty はサーバー上にないため、同梱の `fake-term` が pty の親側で端末の代わりをします。

- termway の起動時の問い合わせ（`CSI 16 t`、`CSI 14 t`、DA1、Kitty graphics の `a=q`、DECRQM 1016）に Ghostty 相当の応答を返す
- termway が書いたバイトを秒単位で数える（**出力バイト/秒はこの実測値**）
- シナリオの入力を stdin に書き込む。キー入力はすべて、termway → 仮想キーボード → foot という本番の経路を通る
- `--throttle-kbps` を付けると読み取り速度を制限し、細い回線をまねる。pty のバッファが埋まると、termway の書き込みがブロックする

fps・タイル数・ヒット率・CPU 使用率は termway の `--stats` の値です。CPU 使用率は 1 コアを 100% とした値です（`/proc/<pid>/stat` の utime+stime）。sway CPU は、termway が起動したコンポジタープロセスの値で、foot は含みません。

シナリオ:

- **(a) 静止**: foot にプロンプトが出ているだけの状態
- **(b) 連続タイピング**: `the quick brown fox jumps over the lazy dog ` を 10 文字/秒でプロンプトに入力し続ける
- **(c) 連続スクロール**: `while :; do ls -R /usr; done`（1 回分は 53,552 行・約 0.9MB なのでループさせる）
- **(d) ページスクロール**: `less /usr/share/common-licenses/GPL-3` で `j` を 30 回/秒送り、1 行ずつスクロールする（暫定計測で追加）

用語:

- 実効 fps: 出力を伴ったキャプチャの数/秒（Phase 4 の高画質化だけの出力は含めない）
- 更新タイル: 表示内容が実際に変わったタイル（Phase 1/2 は送った領域のタイル数）
- 送信画像: 画像データの転送回数（フレーム・damage 矩形・半解像度画像・新規タイル）
- ヒット率: タイルを描くときに、端末側のキャッシュ済み画像を再配置で済ませられた割合

再現方法: `scripts/bench.sh`（[README](../README.md#計測) を参照）

## Term.Everything との比較の前提

Term.Everything の値は計算値です（自分では計測していません）。毎フレーム全画面を RGBA・無圧縮で、15fps で送ると仮定しています。

- 等倍（2538×1260）では、1 フレームは base64 込みで 17.06MB。15fps で **約 256MB/s（244MiB/s）**
- 内容にかかわらず毎フレーム全画面を送るため、静止画面でも同じ量になる

表の「Term.Everything 等倍比」は、この 244MiB/s に対する比です。

## 考察

1. **静止・入力中心の用途では桁違いに減る。** 静止画面では Phase 2〜4 の送信量が 0 になります（copy_with_damage は変化があるまで返らない）。タイピングは 3〜4KiB/s で、Term.Everything 等倍の 1/60,000 程度です。
2. **全画面を毎フレーム送る方式でも、zlib と RGB だけで 1/400〜1/500 になる**（Phase 1、静止）。端末画面は背景が多く、よく圧縮できるためです。写真や動画のような内容では、この比率はずっと悪くなります（今回は計測していません）。
3. **スクロールでは Phase 4（動いている間は半解像度）が最小**（2.2〜2.4MiB/s、Term.Everything の 1/100 程度）。細い回線では差が fps に直接出ます（Phase 1 は 5.4fps、Phase 4 は 11.6fps）。
4. **タイルキャッシュは、内側の端末のセルが外側と揃っていないと逆効果になり得る。** foot の既定フォントでは、スクロールのたびに文字の切れ目がずれ、新規タイル（1 個あたり base64 込みで約 200B）が大量に出ます。その結果、Phase 3 の出力は Phase 1 より多くなりました（9.8MiB/s 対 5.6MiB/s）。セルを揃えるとヒット率は 99% を超え、3.8MiB/s・28fps・CPU 34% に改善します。揃えたあとの主なコストは、1 タイルあたりの「削除（`d=c`、16B）」と「再配置（`a=p`、約 22B）」のエスケープシーケンスです（[内訳](#セル揃え時のスクロール-phase-3-の出力内訳)）。
5. **CPU の律速点。** Phase 1/2/4 のスクロールは、全画面または半解像度画像の zlib 圧縮と全タイルのハッシュ計算で約 18〜20fps に留まります（termway の CPU 60〜70%）。sway の pixman 描画と screencopy のコピーで、さらに 25〜30% 使います。初版の考察です。その後、変換・ハッシュ・圧縮を並列化しました。
6. **ページのようなスクロールは、送信済みの画像をずらすのが最も安い**（暫定計測）。新しく見えた帯だけを等倍で送るので、半解像度で送り直すより転送量が少なく、スクロール中もぼやけません。3800×1890px では 1.73 MiB/s → 768 KiB/s、15fps → 25.6fps でした。1 フレームで大きくずれる場合（`ls -R` を流し続けるなど）は、半解像度で送り直す方が安いので、自動でそちらに切り替えます。

## 計測中に見つかった問題と対策（抜粋）

詳細は [DESIGN.md](DESIGN.md) を参照。

- キャプチャが約 1fps しか出なかった: `buffer_done` の処理中に送る `copy` リクエストを flush せずに poll で待っていた。poll の直前に必ず flush するよう修正
- foot のフォント設定: `pixelsize=15` でもセル幅は 8px。`letter-spacing=1px` で 9px に揃う（マウスのセル座標が一致することで確認）
- タイピングで余計なタイルが出る: headless 出力にはハードウェアカーソルがないため、sway のポインタがフレームに描き込まれる。`seat * hide_cursor 1000` と `hide_cursor when-typing enable` を設定
- 細い回線で Phase 4 が劣化した（0.3fps）: フレーム間隔が高画質化の待ち時間（200ms）を超え、動いている最中でも「静止」と判定していた。静止の判定を「2 回のキャプチャで変化なし」または「コンポジターから damage が 200ms 来ない」に変更
